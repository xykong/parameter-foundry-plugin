# Migration Execution Decisions

- Date: September 15, 2026
- Scope: how the single migration wave is prepared, executed, and accepted
- Status: decided; the open organisational inputs are listed at the end with the
  default this plan already assumes

The goal is that every production Job which uses a source parameter family is
replaced by the unified controls, and that the replacement is **proven by
simulation before the wave** and **by A/B evidence during the wave**. A Job that
cannot be replaced losslessly must be visible as such with a concrete redesign
task, not silently skipped.

## Definition of done

1. Every Job on the controller that uses a source parameter family has a
   simulation row from
   `…/unified-parameters-replacement-simulation/report` (read-only, admin).
2. Every parameter of those Jobs is in one of these states:
   - `EQUIVALENT` or `EQUIVALENT_ADDED_ENV`: the replacement reproduces the
     recorded value and the environment export.
   - `EQUIVALENT_WITH_HISTORY`: the current behavior is reproduced; older builds
     used values the source control no longer offers either.
   - `NEEDS_ORDER_DECISION`: the environment export carries the same values in a
     different order. The Extended Choice migration sets
     `environmentExportOrder: submitted`, which removes this state for that
     family; the verdict stays as a safety net for other families.
   - `NEEDS_PROVIDER`: the target is a governed Provider; the recorded values
     become the Provider's required value contract before it is enabled.
   - `MANUAL_REDESIGN`: the source cannot be converted automatically; the Job
     carries a redesign task and a recorded value contract to preserve.
   - `UNVERIFIED`: the Job never recorded a value for the parameter; it needs one
     representative build with that parameter before it is accepted.
   - `MISMATCH`: the recorded value is not representable or the export changed;
     this blocks the wave until it is resolved.
3. After the wave, every migrated Job has A/B evidence (`PASS`) recorded on its
   migration record.

## Decisions

### 1. One wave, no partial migration

Migration runs once, after the simulation is complete and every `MISMATCH` is
resolved. Preparation and migration are separate activities; a half-migrated
controller is not an acceptable intermediate state.

### 2. Execution order inside the wave

1. Extended Choice static parameters (mechanical mapping, decisions from the
   adapter).
2. List Git Branches parameters, after their Connection Profiles exist.
3. Active Choices parameters, re-authored against Providers or a Unified Form.
4. Stashed File parameters stay native (ADR 0015) and are recorded as a
   deliberate boundary, not as a migration.

The order keeps the mechanical work in front of the work that needs a redesign
conversation, so any unexpected finding is discovered while the risk is still
low.

### 3. Generated Jobs migrate in the repository

Branch Jobs generated by multibranch or organization folders carry the
parameters materialized from their Jenkinsfile. Migrating their Job
configuration would be overwritten on the next branch build, so those Jobs are
migrated in the repository Jenkinsfile (or the branch project configuration) and
re-scanned afterwards. The migration plan lists them per project, and the same
A/B evidence gate applies.

### 4. Connection Profiles are administrator-owned

Every repository or service the unified Providers reach is bound through a
Connection Profile. The migration inventory produces the required profile list
(authority, path allow-list, credential reference) from the source parameters;
repository URLs and credential IDs are never copied into Job configuration or
into the migration records.

### 5. Active Choices is a redesign, not a conversion

Active Choices scripts are not executed during migration. Each Job gets the
generated Provider or Form skeleton, the recorded value contract from the
simulation, and the semantic decisions from the adapter. The redesign is
accepted only when the Job's recorded values are all representable by the new
Provider or Form.

### 6. Stashed File stays native

Uploading a file is a transport capability, not a choice control (ADR 0015).
The unified controls do not replace it. If file upload ever needs a governed
replacement, that is a new product capability with its own design, not part of
this migration.

### 7. Permissions

The simulation needs administrative read access only, so it covers Jobs that the
migration operator cannot configure. Applying a batch needs `Job/Configure` on
the affected Folder; the wave assumes the migration account holds that
permission for every Folder listed by the simulation report. Where it does not,
the Folder owner applies the batch and records the same evidence.

### 8. Acceptance per Job

A migrated Job is accepted when a representative build with the migrated
parameter produces `PASS` A/B evidence (same canonical value, same environment
export, same downstream value) and the Job's build succeeds. A build that only
proves the Job still runs is not sufficient.

### 9. Rollback

Every batch keeps its pre-migration Job XML, every release keeps the previous
HPI under `JENKINS_HOME/.unified-parameters-rollback/`, and a batch rollback is
refused once the Job changed afterwards, so a manual edit is never overwritten.

## Organisational inputs this plan assumes

These are the only items this plan cannot decide by itself. Each has a default,
so the work continues without waiting:

| Input | Default this plan assumes | Effect if different |
|---|---|---|
| Who reviews and merges the repository Jenkinsfile changes for generated Jobs | The owning team merges them through its normal review, with the generated patch from this migration | The generated Jobs move only after their merge |
| Migration window | A low-traffic window per Folder, with the Folder owner notified before the batch runs | Windowing changes the schedule, not the plan |
| Migration account | An account with `Job/Configure` on every affected Folder (or the Folder owner applies its own batch) | Batches stay with the Folder owner |

## Simulation Result

September 15, 2026 on `0.3.182-SNAPSHOT`: 208 Jobs, 277 parameters, 1,244
replayed production values, **0 `MISMATCH`**. 167 parameters are equivalent
(including four whose older builds used values the source no longer offers), 98
need their Provider or Form completed, 6 have no recorded value yet, and 6 need
a business redesign or stay native. The wave therefore has three preparation
lists and no unknown conversion risk: Providers to create for 61 Jobs, a
representative build for 5 Jobs, and 6 redesign/native items.

September 16, 2026 on `0.3.187-SNAPSHOT` extended this to a per-Job verification
with definition and default checks: 208 Jobs, 277 parameters, 2,238 replayed
values, **0 `MISMATCH`**, every one of the 173 Extended Choice parameters with a
matching option set, 138 parameters `EQUIVALENT`, 3 `EQUIVALENT_WITH_HISTORY`,
3 `EQUIVALENT_DEFAULT_ONLY`, 28 `NEEDS_DEFAULT_DECISION`, 98 `NEEDS_PROVIDER`,
1 `UNVERIFIED`, and 6 `MANUAL_REDESIGN`. The Connection Profile inventory is
four Profiles across two hosts and two credential references for 43 Jobs, and the
per-Job manifest carries each parameter's target snippet and value contract.
