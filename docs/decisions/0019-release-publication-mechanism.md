# ADR 0019: Release Publication Mechanism

- Status: Accepted
- Date: September 22, 2026
- Related: [ADR 0016](./0016-single-hpi-product-packaging.md),
  [ADR 0017](./0017-product-renaming-to-parameter-foundry.md),
  [ADR 0018](./0018-public-hygiene-and-private-lab-overlay.md)

## Context

Every release so far was published by committing the built HPI into `dist/` and
recording its digest in `CHANGELOG.md`. That serves the maintainer's own
controller, but it is not how a Jenkins community plugin reaches users:

- Jenkins publishes plugin artifacts in `repo.jenkins-ci.org`; the update
  center, `plugins.jenkins.io`, and the plugin manager read from there.
- Upload permission is granted per artifact through the
  [repository permissions updater](https://github.com/jenkins-infra/repository-permissions-updater),
  and the plugin source must live in the `jenkinsci` GitHub organization.
- Jenkins recommends JEP-229 continuous delivery: a GitHub Actions workflow
  rebuilds the default branch and deploys it to Artifactory, so no maintainer
  credentials and no local build take part in a release.
- The archetype's Release Drafter drafts a release named `0.1` tagged
  `parameter-foundry-0.1`. That tag cannot exist: the project's third version
  field is the commit count, and the current release is `0.4.255`.
- Hosting starts from a public repository: the Jenkins hosting team forks it
  into the `jenkinsci` organization and asks the maintainer to delete the
  original. The sanitized repository therefore has to be public before the
  hosting request, not after it.

The project also needs its release history to stay meaningful: `CHANGELOG.md`
has a section per release, the lab overlay has a dated deployment record per
release, and ADR 0017 pins the names of artifacts that were already published.

## Decision

### Publication path

Parameter Foundry is published as a Jenkins community plugin: artifacts go to
`repo.jenkins-ci.org` and the update center distributes them. The public `xykong/parameter-foundry-plugin` repository is the pre-hosting
source channel. Historical HPI archives are private and outside Git; official
update-center distribution has not started.

### Release automation

The project adopts JEP-229 CD in its `workflow_dispatch`-only form: the CD
workflow from the `jenkinsci` template releases on demand, from a commit whose
ci.jenkins.io build passed. Merges never release automatically, because every
release here is a deliberate act with a CHANGELOG section, acceptance evidence,
and a lab record.

`maven-release-plugin` is not used, and no release is published from a
developer machine.

### Version format

The version keeps the project's meaning and takes its numeric component from
the repository, using the manually controlled prefix form of the CD changelist:

```xml
<version>${revision}.${changelist}</version>
...
<properties>
  <revision>0.4</revision>
  <changelist>999999-SNAPSHOT</changelist>
</properties>
```

with `.mvn/maven.config`

```text
-Pmight-produce-incrementals
-Dchangelist.format=%d.v%s
```

A release is then `0.4.<git-depth>.v<commit-hash>`, and a snapshot is
`0.4.999999-SNAPSHOT`. The third field keeps its current rule: on a linear
`master` the git depth is the commit count. The first two fields stay manual
and are incremented when the release scope changes. The release tag is
`parameter-foundry-<version>`.

Verified on September 22, 2026 by applying the change to a scratch worktree:

```text
mvn validate help:evaluate -Dexpression=project.version
  → 0.4.999999-SNAPSHOT
mvn validate help:evaluate -Dexpression=project.version -Dset.changelist -Dignore.dirt
  → 0.4.258.ve8a_9e5e644b_9
```

The commit under test is the 258th on `master`, so the computed number equals
the commit count. The changelist extension escapes the commit hash for Maven,
which is why the reference contains `_`.

Both poms carry the placeholders: the reactor root declares
`<version>${revision}.${changelist}</version>`, and `plugin/pom.xml` references
the parent with the same expression.

### Release notes

`CHANGELOG.md` stays the repository's release record: every release adds its
section before the release is triggered. GitHub release notes are generated by
the CD workflow once CD is enabled. The archetype's Release Drafter
configuration and workflow are removed now: its templates derive tags from
`$NEXT_MINOR_VERSION` and cannot express this version scheme, and the CD
workflow subsumes it.

### Artifact retention

For public-source preparation, historical `dist/` HPIs are retained in a
private artifact archive and excluded from the public checkout. Old artifacts
may embed deployment-specific identifiers even when current source is clean.
Historical artifact paths and hashes in verification records identify those
archived files; they do not promise availability in the public repository.
New release binaries must be distributed separately from source control.
After hosting, Artifactory is the authoritative public artifact source.

Interim releases prepare `<revision>` using the next `master` commit count and
record the release scope in `CHANGELOG.md`. Build and verify the exact HPI from
the pinned parent commit plus the explicitly reviewed release metadata changes,
then retain that HPI and its digest outside the public source repository.
Record the actual build inputs and SCM markers; do not describe this artifact as
built from the later commit that retains it. After committing, verify the commit
count, version and artifact digest before creating the local release tag. A
public push remains a separate authorized action. This interim procedure ends
when the first Jenkins CD release replaces local HPI distribution.

## Consequences

- Users receive the plugin through the update center with versions like
  `0.4.258.ve8a_9e5e644b_9`. The first release notes must state the format
  change, because it differs from every version published before.
- A release needs no maintainer credentials: the CD workflow builds the
  default-branch commit, deploys it, and creates the tag.
- The public repository stops accumulating binary artifacts.
- The lab overlay remains the only record of the real deployment, as ADR 0018
  requires.
- Release timing stays explicit: the maintainer triggers the workflow after
  the CHANGELOG, the acceptance evidence, and the lab record are in place.

## October 29 hosting preparation update

The official local Hosting Checker now requires Jenkins 2.555.3, plugin parent
6.2236.v12dd4c483242, and the current 2.555 BOM. The development release line
therefore moves to 1.28 with Java 21 and `1.28.999999-SNAPSHOT`; old release tags
retain their original prerequisites.

The former single-module reactor is consolidated into a root HPI POM with the
actual artifact ID `parameter-foundry`. Source and artifact paths remain
`plugin/src/` and `plugin/target/`; the child POM is removed. This supersedes the
older two-POM arrangement above and exposes real dependencies to the hosting
checker. The BOM remains necessary for those dependencies.

The CD workflow is derived from the Jenkins template, uses only manual dispatch,
and is guarded to run in the `jenkinsci` organization. Adding it does not publish
a release or imply that hosting or release permissions have been granted.
The existing README installation instructions remain useful until update-center
publication; the hosting checker's removal suggestion is conditional on hosting.

Hosting request [#5412](https://github.com/jenkins-infra/repository-permissions-updater/issues/5412) was submitted on October 29 with GitHub and Jenkins community user `xykong`. The official local checker passed with no Required findings. The conditional `structs` recommendation is inapplicable because the implementation uses `SymbolLookup`; source-build instructions remain until official distribution is available. The final BOM is `7237.v5071b_f4589f1`. Both complete Maven verification runs passed 558 tests with zero failures, errors, or skips on macOS/JDK 25. Hosting acceptance, organization invitation, CI, release permissions, and the first official release remain pending.

## Standard layout follow-up

The single HPI now uses Maven's standard `src/` and `target/` directories. This
supersedes the temporary path-preserving root POM arrangement above. The official
checker recognizes actual structs usage under the standard source root; the
explicit dependency remains because runtime SymbolLookup is required. Current
installation details live in the user guide. Earlier tags and dated artifact
records retain their historical paths.
